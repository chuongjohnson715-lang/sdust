# 01 ｜ 取数方案：不下载整包，只取需要的字节

> 目标：把「一节 4 GB 的录播」压到「约 96 MB 的必要证据」，同时保证证据可回溯。

## 1. 为什么不能直接下载

| 做法 | 单节体积 | 结果 |
|---|---|---|
| 整包下载 / ffmpeg 直连直链 | ≈ 4.2 GB | 慢、失败率高；直连还会被 WAF 按 TLS 指纹拦成 403 |
| 只取音频 | ≈ 34 MB | 省钱，但没有课件画面证据 |
| **音频 chunk + 关键帧（本仓库默认）** | **≈ 96 MB** | 时间分辨率受采样步长限制 |

真正要用的只有两样东西：**老师说的每句话**、**每页课件讲的是什么**。
其余 97% 是重复的静止画面和与音频交错的视频数据。

## 2. 音频：按 chunk 精准 Range

MP4 的 `mdat` 里音频与视频交错存放（实测音频 chunk 约 660 B，间隔约 23 KB 视频数据）。

1. 只取文件头部，解析 `moov → trak(mdia.hdlr=soun) → stbl` 的 `stco / stsz / stsc / stsd`，
   算出**每一个音频 chunk 的绝对字节范围**；
2. 对每个范围单独发 HTTP `Range` 请求，中间的 23 KB 视频**一个字节都不下**；
3. 按 ADTS 重新封装成 `.aac`，再转 **16 kHz 单声道 wav** 交给 ASR。

实测：五万多个 chunk、8 并发、单 chunk 约 9 ms → 全量约 1 分钟 / 34 MB。

> 关键实现：[`scripts/audio_chunks.py`](../scripts/audio_chunks.py)；
> MP4 结构解析复用 [`scripts/audio_extract.py`](../scripts/audio_extract.py) 里的 box 遍历函数。

## 3. 视频：只下关键帧

H.264 的 IDR 帧可独立解码，不必下载整段 GOP。

1. 解析 `stss` 得到关键帧索引（演示类录播通常每 1 秒一个，全片数千个）；
2. 按采样步长（默认 15 s）挑最近的 I 帧，只对这些帧发 Range；
3. 从 `avcC` 取 SPS/PPS，把 AVCC（4 字节长度前缀）转 Annex B（`00 00 00 01`），
   拼成 `[SPS][PPS][IDR]` 交给 ffmpeg 单独解码出图。

实测：441 个采样点 × 单帧约 140 KB ≈ **62 MB**，占全片约 2.4%。

> 实现：[`scripts/keyframe_frames.py`](../scripts/keyframe_frames.py)。

## 4. 抽帧去重：变化检测，不用场景检测

- 采样后逐帧与**前一帧灰度图**做像素差分，变化率超过阈值（默认 2%）才算新页；
- 只保留前一帧灰度图 → 内存常数级；把全片帧累积进列表会到 GB 级并 OOM；
- 不用 dHash：对压缩噪声过敏；不用 ffmpeg `select='gt(scene,…)'`：每门课都要重调参。

代表帧回抽全分辨率后再做 OCR，时间分辨率受采样步长限制。

## 5. 两条取数路线

| 路线 | 适用 | 输入 | 代价 |
|---|---|---|---|
| **A 双轨** | 平台允许下载整包，或本地已有双路 mp4 | 摄像机轨 + 屏录轨 | 磁盘大，但时间分辨率 2 s、课件页最全 |
| **B 轻量（默认）** | 平台拦整包 / 想省流量 | 音频 chunk + 关键帧 | ≈96 MB/节，时间分辨率 15 s |

轻量路线会先把「音频 + 抽帧」合成一条屏录 mp4，再喂给同一条主管线，
所以**证据层代码零改动**，产物结构与双轨版一致。

## 6. 403 的真实原因与三条硬约束

实测结论：同一签名直链，换遍 UA / Referer / Origin / Cookie 六种组合，
**全部返回同一个 403**，而 TCP 层完全可达 → **403 是签名过期，不是请求头缺失**。

因此：

1. **现取现下**：每次下载前重新取播放器配置拿新直链；
2. **旧直链不可复用**：`tracks.json` 里的 URL 只当记录，下载前必须过新鲜度守卫
   （`light_common.is_url_fresh / assert_fresh`，默认 30 分钟上限）；
3. **必须走浏览器网络栈**：`Playwright context.request` 发 Range；
   ffmpeg / urllib / OpenCV 直连会被 WAF 按 TLS 指纹拦截。

另有两条省流量细节：

- 取配置时先**阻断存储域（`:8804` 一类的媒体域）**，否则播放器会自动拉预览流，
  每次白下 200 MB+；
- 播放器分片请求的 resource_type 可能是 `xhr` 而非 `media`，**按域名阻断**才可靠。

> 实现：[`scripts/captures_api.py`](../scripts/captures_api.py)、
> [`scripts/fetch_tracks_v2.py`](../scripts/fetch_tracks_v2.py)、
> [`scripts/light_common.py`](../scripts/light_common.py)。

## 7. 一次取数的完整时序

```
登录（会话持久化复用，人工只过首次验证码）
  → 打开播放页，阻断媒体域
  → GET player-url → GET embed-token → GET captures
  → 解析 lesson_videos[]：区分音轨 / 视频轨、拿到两条签名直链
  → 音频：moov 解析 → N 个 Range → aac → 16k wav
  → 视频：stss 解析 → 采样点最近 I 帧 → Range → 解码 → jpg → 变化检测去重
  → 合成一条屏录 mp4（音频 PCM 直通，不二次压缩）
  → 交给 12 阶段主管线
```

## 8. 自测与验收

```bash
# 直链新鲜度守卫（不需要登录）
python scripts/test_light_common.py

# 单节全流程（取数 + 管线 + 语义 + 五件套）
python scripts/run_lesson_browser.py \
  --activity <活动id> --date <YYYY-MM-DD> --course "<课程名>" \
  --course-id <课程id> --deliver-root ./_work/deliver
```

通过标准：

- `test_light_common.py` 全部 PASS（存储节点不可达时允许 SKIP preflight 一项）；
- 单节落在磁盘上的 `light/audio/raw_16k.wav` 时长与录播时长相差 < 5 s；
- `light/slides/slides.json` 的页数与人工浏览播放器所见页数量级一致。

## 9. 代价与边界（必须先说清楚）

| 代价 | 说明 |
|---|---|
| 时间分辨率 | 轻量路线默认 15 s，无法定位「第 12 分 37 秒那一页」；需要更细就调小步长，流量线性上涨 |
| 缺整段视频 | 无法复查板书过程、鼠标轨迹、动画中间帧 |
| 依赖平台接口 | 端点是内部接口，平台改版就要重做取配置（只影响取数层，不影响证据层） |
| 只读边界 | 全程只做 GET / 播放，不提交、不发帖、不改任何资料 |

> 下载前必须先声明「取数形式 / 预计流量 / 会缺什么」，再动手（见 `AGENTS.md` §2）。
